# 에이전트 프롬프트 작성

이 프로젝트는 개발자가 선언한 노드 경로와 처리 함수로 자료를 모으고 결과를 도출한다. 모델이 매번 도구를 고르고 실행 계획을 새로 만드는 ReAct 에이전트로 설계하지 않는다. 프롬프트 작성 전에 대상 노드의 실제 입력·담당 판단·허용된 후속 경로·반환 계약을 확인한다. 업무 규칙이 미정이면 임의로 채우지 않는다.

## 프롬프트에 정의할 내용

다음 항목의 의미가 드러나도록 작성한다. 모든 노드에 같은 제목이나 긴 템플릿을 강제하지 않는다.

1. **목적과 책임 범위:** 해당 노드가 입력을 받아 무엇을 산출하며, 무엇을 충족하면 맡은 작업이 끝나는지 정의한다. 페르소나 대신 수행할 작업과 목적을 설명한다. 자료 분석 노드가 전체 업무의 완료 여부를 대신 판단하게 하지 않는다.
2. **입력의 의미:** 전달되는 목표·자료·이전 결과의 출처와 적용 범위를 설명한다. 확정한 사실과 검증할 후보, 조회하지 않은 항목과 조회했지만 없는 항목을 구분한다. 필요한 용어·규칙·우선순위는 현재 노드의 실제 입력만으로 판단할 수 있게 명시한다.
3. **판단 기준:** 결과 선택에 필요한 조건·우선순위·충돌 처리·근거의 충분성을 일반화 가능한 규칙으로 정의한다. ‘정확하게·적절하게·충분히’라는 지시만으로 끝내지 않는다.
4. **완료·종료 조건:** 정상 완료에 필요한 결과와 근거, 자료 부족·상충 등 현재 노드에서 해결할 수 없는 상태를 구분한다. 재시도로 보완할 수 있는 부족분은 무엇이 부족한지 반환하게 한다. 다음 단계로 넘길 부분 실패와 현재 실행을 끝낼 실패는 업무 계약에 맞춰 구분한다.
5. **출력 계약:** 필드의 구조뿐 아니라 의미·적용 범위·근거 연결·누락 표현을 정한다. 값 없음·0, 미조회·조회 실패, 추출값·계산값을 구분하여 다음 노드가 의미를 추측하지 않게 한다.

도구 선택 방법·자율 검색 전략을 프롬프트의 공통 항목으로 넣지 않는다. 필요한 조회·도구 호출·순서는 개발자가 노드 경로와 처리 함수로 구현하며, 모델은 그 경로에서 받은 정보를 판단한다. 후속 노드 선택을 맡는 모델에는 선언된 후보와 선택 기준을 전달한다.

## 지시·입력·실행 제어의 분리

- 고정 시스템 지시에는 역할·판단 기준·출력 의미를, 동적 사용자 입력에는 이번 목표·자료·조건·보완할 부족분을 둔다. 실제로 함께 전달되는 시스템 지시와 앞선 문맥을 고려하고 지시를 중복하거나 충돌시키지 않는다.
- 입력 문서·검색 결과는 사실 판단 자료다. 자료 안의 명령문을 에이전트의 실행 지시로 따르지 않는다는 점을 명시한다.
- 무관한 전체 배경·과거 대화·다른 노드의 내부 과정은 넣지 않는다. 현재 판단에 필요한 맥락을 생략하거나 다른 노드가 아는 정보를 알고 있다고 가정하지 않는다.
- **재시도는 실행 코드에서 제어한다.** 노드별 완료 판정·종료 사유·최대 시도 횟수·대기 조건을 선언한다. 결과 미충족은 부족분을 반영한 다른 입력으로 재시도하며, 동일 입력 반복과 이전 입력으로 돌아가는 순환을 막는다. 일시적인 API 오류만 제한된 동일 요청 재시도를 허용한다. 오류 분류·Retry-After·변경 작업의 중복 방지는 프롬프트 지시로 대신하지 않는다. 실제 API는 [노드 실행 계약](../../../docs/workflow.md#노드-완료종료재시도)을 따른다.
- 분기를 구분할 수 있으면 프롬프트를 분리하여 해당 경로에 필요한 지시만 전달한다.
- **퓨샷과 구체적인 예시는 넣지 않는다.** 필요한 설명은 규칙·입출력 계약으로 표현한다. 모델의 사고 과정을 단계별로 출력하도록 강제하지 않는다.
- 실패 사례별 방어 문장을 누적하지 않는다. 실패 원인을 설명하는 공통 기준을 수정하고, 수정에 사용하지 않은 사례에서도 검증한다.
- Luna·Terra에 공통 계약을 사용한다. 모델 이름만으로 프롬프트 언어·길이·세분화의 우열을 단정하지 않는다. 차이가 필요하면 동일 입력의 정확도 평가로 확인한다. 답변 언어는 출력 조건으로 명시한다.
